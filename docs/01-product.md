# 01 · 产品定位

版本：v0.1 讨论稿｜2026-10-23

## 1. 一句话定义

**Pulsar Dock · AI Agent 安全协作工作台。**

让用户已有的 Agent 在独立、受控的环境里工作；让 Agent 在授权范围内寻找协作者；让用户始终能看清权限、过程和成果。

不是另一个聊天窗口，不是 Docker 参数编辑器，也不要求所有 Agent 换成我们自己的执行循环。

## 2. 为什么需要它

现有工作方式里，用户往往需要同时承担四件事：配置不同 Agent、交出文件与服务权限、判断执行风险、手动搬运多个 Agent 的工作结果。产品要把这些负担收敛为三件用户能理解的事情：

- **给它什么**：选定项目资料、模型服务和可使用的工具。
- **允许做什么**：在副本中修改、调用哪些服务、能否创建协作者。
- **拿回什么**：查看差异、测试证据和审查结论，再决定是否应用。

题目中的“不在沙箱里填写敏感信息”是核心体验，也是安全架构约束：用户在可信界面配置或连接服务，Agent 只拿到受限访问入口，不拿到上游密钥。

## 3. 用户与主要场景

[建议] 首批用户是已经使用 Coding Agent、但不愿反复配置或给予整机权限的个人开发者和小团队。界面面向会选择项目、描述需求的人，不要求理解容器、网络命名空间或 MCP JSON。

### 场景 A：放心让 Agent 改一个项目

选择项目和 Agent → 查看访问范围 → 启动 → Agent 在独立副本中修改与测试 → 用户检查变更 → 明确确认后应用到原项目。

成功不是“终端启动了”，而是原项目未被静默改写，结果能拿回，失败能解释。

### 场景 B：多 Agent 协作与对抗性审查

主 Agent 接到需求 → 请求 Dock 创建一个或多个限定权限的 Agent 环境 → 不同 Agent 分别执行开发、测试、审查或方案比较 → 通过 Dock 交换消息和固定版本成果 → 主 Agent 汇总 → 用户审阅。

Dock 不只支持“一个主 Agent + 一个审查 Agent”。同一项工作可以交给多个 Agent 或不同 Harness 独立完成，再对比它们的实现、测试结果、审查意见和资源消耗。对于安全、架构和关键代码任务，可以让多个 Agent 互相审查，形成对抗性审查，而不是只依赖单一 Agent 的自检。

所有审查和对比都绑定明确的成果快照，不读取持续变化的共享目录；不同 Agent 之间不能因为参与同一任务就自动获得彼此的全部文件和权限。

### 场景 C：复用已经配置好的模型与工具

连接已有 Magpie 或提供兼容的服务 → Dock 检查能力 → 生成沙箱专用配置 → 用户不用重复填写 Agent 的技术配置。

导入配置不等于复制凭据，也不等于依赖和运行环境自动迁移成功。

## 4. 产品原则

1. **安全优先于便利。** 安全检查失败时阻止启动或拒绝请求，不偷偷回退成宿主直接执行。
2. **常用路径简单，边界可解释。** 默认显示“只能修改副本”“只能访问选定工具”，高级参数收在诊断页，但实际权限不隐藏。
3. **人和 Agent 共用平台能力，不共用权限。** 两种入口调用同一套任务、环境和成果服务；用户审批权限不暴露给 Agent。
4. **接入成熟 Agent，不重新实现所有 Agent。** 保留原生终端或官方交互能力，统一可验证的生命周期和交付对象。
5. **把差异说成人话。** 有的 Harness 能续接历史会话，有的只能重新运行；有的能提供工具执行事件，有的只有终端输出。Dock 应明确显示这些区别，不把重跑叫恢复、不编造进度。创建协作者是 Dock 提供的公共能力：只要 Agent 能通过适配的 MCP/工具接口调用 Dock，就不要求 Harness 原生具有多 Agent 功能。
6. **局部失败不扩大授权。** 连接故障、版本变化或模型不可用，应停止受影响功能而非自动更换账户或放开网络。

## 5. 产品边界

### 产品应覆盖

- 桌面入口、环境准备、项目隔离、运行管理。
- 模型与 MCP 的受控连接、凭据外置、授权与撤销。
- 多 Agent 环境创建、消息、任务关系、成果交接和资源限制。
- 多 Agent 对抗性审查、不同 Harness 的并行执行与结果比较。
- 运行记录、变更查看、人工应用与可解释失败。

### 首版不承担

- 重做完整模型协议转换服务或 Magpie。
- 强制统一所有 Agent 的推理、内部上下文、技能和记忆机制。
- 企业多租户云平台、跨机器集群调度、无人值守生产部署。
- 保证任意恶意内核漏洞无法逃逸，或保证所有授权输出都没有敏感内容。
- 将跨设备实时查看、语音或特定投屏协议当作核心闭环的前提。

完整功能与比赛范围在 [02](02-features.md) 和 [05](05-delivery.md) 分别定义。

## 6. 与 Magpie 的关系

Pulsar Dock 是完整的主产品形态：负责桌面入口、安全环境、权限、Agent 协作、成果交接和用户审阅。它不要求用户理解底层 Agent 的内部实现，也不把某一个 Agent Harness 作为产品前置条件。

Magpie 是可选的模型与配置配套组件：连接已有安装，未来可经同意配套安装。Dock 独立运行，不 fork 它来承载整个产品，不覆盖用户已有全局配置。没有 Magpie 时允许接入与所选 Agent 协议兼容的模型服务，不承诺自行转换任意协议。

## 7. 成功是什么

[建议] 产品成立至少同时满足：

- 用户能不编辑技术配置完成一次任务。
- 文件边界、凭据边界、网络边界有实际反例测试，不只是界面上的绿色标记。
- 主 Agent 真正通过 Dock 创建子环境，用户能看到任务关系与真实成果。
- 原项目、日常 Agent 配置和其他服务不因一次任务被静默改变。
- 错误、权限拒绝、未适配能力都能解释并给出下一步。

比赛是这个产品的第一段可执行闭环，不是产品范围的永久上限。名称重名、商标、分发许可证和商业模式不在本次已确认结论中。
